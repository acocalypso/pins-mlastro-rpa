# Integration bundle and recovery

This is an experimental integration, not a generally validated drop-in release. The tested host baseline is PINS 3.3.0.1058 nightly (.NET 10), TPPA 2.2.8.0, ninaAPI 2.2.15.2, Touch-N-Stars 6.5.0-beta22-beta and RPA firmware 1.13.0. A previous build completed a sky TPPA alignment on November 6. The new 0.2 features and this exact bundle still need supervised hardware and end-to-end acceptance testing; repeated camera stress remains unresolved. Make sure the exact four built components were tested together on your target before installing. A bundle checksum detects accidental changes, not malicious substitution: obtain it through a trusted channel and independently verify its release hash/signature.

A bundle contains the Linux plugin, its Linux ARM64 single-file worker, a *full* compatible ninaAPI build containing the relay, and the built web frontend. It does not contain PINS, TPPA, host DLLs, credentials, or a native Android APK. The source export supplies the ninaAPI integration patches and a portable PINS-compatible build project; build the full DLL from the pinned upstream source using compatible PINS dependencies, which are not included. See BUILD.md for source and license obligations. An APK, if needed, is a separate build and installation; this installer does not handle it.

On the Pi you need Python 3.9+, systemd, a running compatible PINS installation, free disk space for backups, and write access to the installation. The service must be active and its MLAstro, TPPA and equipment status endpoints reachable. Identify the actual PINS home, versioned plugin root, installed ninaAPI DLL, frontend web root and systemd service name on your installation. The PINS home, plugin root, ninaAPI DLL and web root may be in separate directories. Supply absolute paths without symlinks or parent traversal; do not use the filesystem root or system directories as destination roots. The installed relay file must be named `ninaAPI.dll`. Snapshots are kept only under PINS home. The frontend root must already exist. Back up the whole installation separately. Stop all observations and make sure the camera is not exposing or in live view, the mount is not slewing, TPPA is stopped, and MLAstro automation and manual/jog movement are stopped. Prevent other users and clients from starting work during installation and recovery; checks cannot eliminate races with other controllers.

Extract the bundle into a trusted, private directory. From there, first check (replace each example path and service name):

```sh
python3 install_bundle.py --check --pins-home /opt/pins --plugin-root /opt/pins/plugins --nina-dll /opt/pins/plugins/ninaAPI/ninaAPI.dll --web-root /opt/pins/web --service pins.service
```

The paths above are examples, not discovered defaults. The check verifies file hashes and rejects unlisted files, then checks MLAstro on port 1891, TPPA on 5000, and camera and mount on 1888. On a first installation only, append `--fresh-install` to allow the MLAstro endpoint to be absent; the other endpoints must still report idle. The installer rejects that option when the MLAstro plugin file is already installed. An unavailable or unrecognized status blocks an upgrade or rollback. Resolve it and rerun the check; do not bypass the guard.

Once the check succeeds, run the same command with `--install` in place of `--check`, and retain `--fresh-install` only for an eligible first installation. Use `sudo` when needed. It checks again, saves every replaced file under PINS home in `.mlastro-backups`, stops PINS, installs the assets before atomically replacing the web entry document, starts PINS and checks status, including the version 2 status and watchdog read-only routes through the newly installed ninaAPI relay. Existing unreferenced web assets are retained. It prints the backup directory; record it. If installation or post-start status checks fail, the installer attempts to stop PINS if necessary, restore the snapshot, and start PINS. If restoration itself fails, the service remains stopped; leave the equipment idle and use the independent installation backup and service logs to recover before starting it.

To restore a previous snapshot, ensure the system is idle and run the same command with `--rollback /opt/pins/.mlastro-backups/BACKUP-NAME` in place of `--check`. Use the same destination paths and service as the original installation. The rollback checks status, stops PINS, restores or removes each touched file and restarts PINS only after a complete restoration. If restoration fails, the service remains stopped for manual recovery. Verify status and functionality afterward. A snapshot covers only files touched by that installation; it is not a full system backup. Keep the bundle and backup private from untrusted modification. Neither manifest hashes nor snapshot data are signed.

The installer does not connect hardware, start an alignment, resume automation, or alter the firmware watchdog. After installation, verify the plugin is available and equipment state is as expected before a supervised acceptance test. USB instability remains unresolved; see VALIDATION.md for actual validation and limitations.


## Using and recovering the controller

Enable MLAstro RPA in PINS, open its entry in Touch-N-Stars, select USB or Wi-Fi, and connect. For a supervised alignment configure the camera, mount and positive TPPA tolerance, confirm adequate slew clearance, and use Start. Stop the session if conditions become unsafe. Manual arrows perform one bounded step per press; select the step size first. Continuous jog is not supported in this release.

If the interface reports a fault, stop work and ensure the equipment is physically safe. Use **Clear fault and reconnect**, then wait for ready status before moving. If the fault persists or a stop cannot be confirmed, do not resume movement; inspect the controller and connection. **Run connection check** shows a snapshot, and **Download diagnostics** creates a report. The report is designed to omit device addresses and paths, but review the file and remove any information you do not wish to share before sending it.

In **Advanced correction settings**, review axis, direction and overshoot options before changing them. The maximum correction step is expressed in arcminutes and defaults to 120 when no value is supplied; it is not the manual arrow step. The firmware communication watchdog protects against communication loss and should remain enabled. Its state can only be read or changed while connected to the RPA over Wi-Fi: stop work, disconnect USB, connect the same RPA over Wi-Fi, open the watchdog section and verify **Enabled**. If disabled, select Enabled, apply it and confirm the displayed readback. You may then disconnect Wi-Fi and reconnect USB. An unknown or unsupported readback does not confirm protection. The installer never changes this setting.
